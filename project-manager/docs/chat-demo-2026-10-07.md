## Observed limitations

The README describes capabilities and reusable onboarding instructions, rather
than a dated task history. The manager nevertheless proposed onboarding steps
as task descriptions and inferred four unsupported task statuses: `open` for
the CI workflow and `done` for each of the three agent/application folders.
The supporting passages establish that these components exist, not completion
events or an open task. These proposals require rejection or correction; they
were never approved or included in answers.

The answer model receives approved facts and question history, but not the
selected project's name or a summary of its pending intake. Its request to
identify the repository therefore exposes a context/clarification gap.

The bridge preserves review isolation and shared state, but successful storage,
citations and protocol execution do not demonstrate semantic accuracy. Follow-up
quality work should distinguish procedural instructions/component descriptions
from actual task instances, require explicit status evidence, and pass enough
project context to avoid asking for already-submitted information. Measure those
changes on labeled cases before claiming improved accuracy.
